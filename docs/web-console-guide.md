# Peerward Web 控制台完整操作指南

> 适用版本：[release.toml](../release.toml) 对应的当前 Peerward canary（Schema 4、Wire major 5）
> 文档基线：当前仓库中的 Web Console、Control API、存储模型和中文界面实现
> 版本与文档入口核对日期：2026-09-21

本文保留基础资源操作的详细说明。当前新增的资源共享、双栈子网/出口、设备条件、
DNS、配置回执、备份与原生升级任务，以[管理方案与操作流程](management-plan.zh-CN.md)
和[实施状态](management-implementation-status.zh-CN.md)为补充。

控制台实现位于 `apps/peerward-console`，主导航为 **概览、设备、共享、访问、问题与维护**。
当前实现进一步按“一人运维”收敛：日常入口只展示需要决定或操作的内容，安装级维护、凭据、Webhook 等放入
**系统工具**。默认中文，支持英文、明暗主题与移动布局；既有资源 URL 继续可用。
初始化由固定 Control/Relay 宿主完成，不为每个网络启动独立容器。

日常流程：创建网络 → 添加设备并确认上线 → 添加共享并选择访问范围 → 检查访问结果 →
检查实际连接与回执。设备加入和共享创建都从一个连续向导完成；复杂规则、底层凭据和系统维护仍留在高级工具中。
创建、授权和暂停均是控制面提交，只有设备观测能证明实际应用。

添加设备时，确认步骤只查询当前邀请关联的设备；从问题页进入则固定对应的申请，刷新仍可继续核对。
批准前必须在设备上独立核对完整指纹。批准完成后可以直接查看设备，或带着该设备进入访问页。
高级设置中的直接加入方式也通过实际邀请状态确认完成；邀请过期、取消或申请被拒绝时提示重新邀请。
共享确认页显示提供设备、目标、访问范围和后端风险提示；局域网及出口还需明确批准网关转发。
逐项入口、步骤与状态由[浏览器回归](../apps/peerward-console/e2e/README.md)覆盖。

日常界面统一使用 **网络、设备、共享、访问、中继服务** 等面向任务的称呼。`Mesh`、`Peer`、`Presence`、`Policy` 等协议和存储术语仍保留在本指南的技术章节、系统维护和技术详情里，但普通运维流程不要求先理解这些概念。加载、首次空状态、筛选无结果和读取失败也分别显示：读取失败提供就地重试；已知 API 错误默认不把内部错误码附在用户提示后，未知错误仍保留代码供排障。
浏览器回归使用隔离测试数据，不代表生产设备连通；运行报告与可再生截图写入 `artifacts/`，视觉回归基线随测试维护。

## 1. 文档范围

本文面向 Peerward 管理员、运维人员、审计人员和只读查看者，说明如何通过 Web 控制台完成以下工作：

- 登录控制台并确认当前角色和权限；
- 查看 Mesh、Peer、Relay、凭据、服务和审计状态；
- 创建及维护 Mesh、Peer、Relay、加入凭证和服务；
- 暂存、激活和撤销 Authority；
- 轮换、激活和撤销凭据；
- 编辑、校验、模拟和替换访问策略；
- 执行最多 100 项的事务性批量禁用或撤销；
- 根据页面错误码和请求 ID 排查常见问题。

Web 控制台是 Control API 的管理前端。它不负责生成或保管离线 Root 私钥、Peer 私钥或 Relay 私钥，也不替代 PostgreSQL、OIDC、TLS、备份、监控和主机部署操作。

> **技术预览提示：** 当前版本只适用于全新 Schema 4 部署，不读取或迁移 Peerward 0.2 数据、配置、客户端状态或 Wire 消息。

## 2. 核心概念

| 概念 | 含义 | 在控制台中的用途 |
| --- | --- | --- |
| Mesh（网格） | 一套独立的地址空间、DNS 后缀、策略、信任和资源集合 | 几乎所有管理页面都需要先选择 Mesh |
| Root | 离线信任根 | 在控制台外保管，只用于签署 Authority 证书 |
| Authority（授权机构） | Root 签名的在线凭据签发机构 | 签发 Peer/Relay 凭据，支持暂存、激活、重叠和撤销 |
| Peer | 加入 Mesh 的 Linux 或 Android 节点身份 | 连接网络、发布服务、参与策略判断 |
| Relay | Peer 接入和 Relay 骨干转发节点 | 在直连不可用时转发端到端密文，并承载控制连接 |
| Join Ticket（加入凭证） | 有时限、一次性使用的加入授权 | 生成 `peerward://join` 链接和二维码供客户端认领 |
| Credential（凭据） | Authority 为 Peer 或 Relay 签发的身份凭据 | 具有 staged/pending、active、overlap、revoked 生命周期 |
| Service（服务） | 某个 Peer 在 Mesh 内发布的 TCP/UDP 端口 | 作为策略模拟和实际访问的目标 |
| Policy（策略） | 按优先级求值的有序访问规则 | 决定新连接是允许还是拒绝 |
| Presence | Peer 当前附着在哪个 Relay 上的短期租约 | 用于在线状态、Relay 负载和拓扑展示 |
| Version | 资源的单调版本号 | 防止用旧页面覆盖其他管理员刚完成的变更 |

## 3. 启动和访问

### 3.1 本地开发环境

首次启动完整开发栈：

```sh
./deploy/compose/bootstrap.sh
docker compose up -d --build --wait
docker compose ps -a
```

默认访问地址：

- Web 控制台：`http://127.0.0.1:28081`
- Control API：`http://127.0.0.1:28080`
- PostgreSQL：`127.0.0.1:5432`
- Relay Peer/骨干端口：`7777`、`7778`

端口可分别通过 `PEERWARD_CONSOLE_PORT`、`PEERWARD_CONTROL_PORT`、`PEERWARD_POSTGRES_PORT`、`PEERWARD_RELAY_PORT` 和 `PEERWARD_BACKBONE_PORT` 调整。

开发 Compose 会把同一个 `PEERWARD_DEV_BEARER` 同时配置给 Console 和 Control，因此控制台代理请求时具有开发环境的管理员权限。该模式不应用于生产。

### 3.2 生产环境

生产环境应通过受信任的 HTTPS Ingress 或反向代理访问 Console。Console 再通过 `PEERWARD_CONTROL_URL` 连接 Control；浏览器只与 Console 同源通信。

生产部署必须满足以下要求：

- 使用 HTTPS，并在可信入口终止 TLS；
- 配置 OIDC Authorization Code、PKCE、state 和 nonce 流程；
- 不向 Console 容器提供数据库口令、Root 私钥或 Control bootstrap token；
- Control 的 `/livez`、`/readyz` 和 `/metrics` 仅放在私有管理监听器上；
- 不把 Console 或 Control 的本地监听端口直接暴露到不可信网络；
- 将离线 Root 私钥移出在线部署目录并加密保管。

相关部署说明见 [deployment.md](deployment.md) 和 [configuration.md](configuration.md)。

## 4. 登录、会话与权限

### 4.1 OIDC 登录

1. 打开 Web 控制台。
2. 打开右上角账户菜单，点击 **重新验证身份**。
3. 在身份提供方完成登录。
4. 登录成功后浏览器返回控制台首页。
5. 查看账户菜单或侧栏底部的角色，确认当前实际权限。

OIDC 组映射的匹配优先级是 `admin`、`operator`、`auditor`、`viewer`。如果用户同时属于多个已配置组，将采用优先级最高的角色。

浏览器会话使用 Secure Cookie；修改请求还必须携带独立的 CSRF 值。控制台会自动完成 CSRF 处理，不应把会话、CSRF、Bearer 或 Join Ticket 写入 URL、聊天记录或日志。

右上角账户菜单的 **锁定控制台** 会以 CSRF 校验撤销当前服务端会话，再进入锁定页。
解锁重新发起 OIDC `prompt=login`、`max_age=0`，并校验身份提供方返回的 `auth_time`。
验证成功后恢复允许的原页面及网络上下文。开发 Bearer 模式没有可撤销的个人会话，因此不显示锁定操作。

### 4.2 角色与能力矩阵

控制台和服务端按能力授权，而不是把角色简单地按大小比较。服务端授权始终是最终依据。

| 角色 | 能力 | 可执行的主要操作 |
| --- | --- | --- |
| `auditor` | `status_audit_read` | 在当前 Web 界面查看状态和全局元数据审计；不能列出或选择普通 Mesh 资源 |
| `viewer` | 上述能力 + `resource_read` | 查看全部资源、拓扑和策略；使用当前已保存策略进行模拟 |
| `operator` | 上述能力 + `resource_write` | 创建、编辑或禁用普通资源；管理 Join Ticket、Service 和 Policy；编辑已有 Mesh |
| `admin` | 上述能力 + `trust_manage` | 创建 Mesh；暂存、激活和撤销 Authority；完成所有普通资源操作 |

更细的操作边界如下：

| 操作 | 最低能力/角色 |
| --- | --- |
| 查看资源、拓扑和当前策略 | `resource_read` / viewer |
| 查看审计和状态 | `status_audit_read` / auditor |
| 创建或编辑 Peer、Relay | `resource_write` / operator |
| 创建 Service/Join Ticket | `resource_write` / operator |
| 禁用 Peer/Relay/Service、取消 Join Ticket | `resource_write` / operator |
| 编辑已有 Mesh 的名称或 DNS 后缀 | `resource_write` / operator |
| 创建 Mesh | `trust_manage` / admin |
| 暂存、激活或撤销 Authority | `trust_manage` / admin |
| 暂存新的 Relay 凭据 | `resource_write` / operator |
| 激活或撤销 Peer 凭据 | `resource_write` / operator |
| 激活或撤销 Relay 凭据 | `trust_manage` / admin |
| 校验或替换策略 | `resource_write` / operator |
| 用当前策略模拟访问 | `resource_read` / viewer |
| 用未保存草稿策略模拟访问 | `resource_write` / operator |
| 批量禁用/撤销 | `resource_write` / operator |

Relay 凭据的激活和撤销仅对具有 `trust_manage` 的管理员展示，Control API 同时校验权限。

## 5. 界面总览

### 5.1 导航和范围

| 入口 | 日常用途 |
| --- | --- |
| 概览 `/` | 今天需要处理的事项、设备在线情况、共享数量、首次设置与最近活动 |
| 设备 `/peers` | 搜索、平台和状态筛选、分页、CSV 导出、设备详情抽屉 |
| 共享 `/services` | 设备服务、局域网资源、互联网出口的统一列表、向导与详情 |
| 访问 `/policy` | 来源设备/设备组的有效权限、原因、模拟；三类共享的授权添加、撤销与恢复 |
| 问题与维护 `/operations` | 当前网络待办按“发生了什么 → 影响范围 → 建议下一步 → 去处理”展示；路径摘要与安装级提醒保持次要 |
| 网络卡片 | 切换网络；进入网络设置 `/meshes?mesh=…` 或所有网络 `/networks?mesh=…`（保留当前网络上下文；旧 `/meshes` 无选择时也显示所有网络） |
| 系统工具 | 操作记录 `/audit`、系统维护 `/relays`、凭据与签发机构 `/authorities`、Webhook 与配置 `/webhooks` |

入口与写入操作按原有角色能力展示并由服务端再次校验。设备、共享和访问三个日常页面只保留
搜索、列表、详情和最常用动作；技术字段、原始 JSON、批量操作、复杂规则和历史恢复通过页面底部的
**高级工具**入口在右侧抽屉中打开。后续章节中的旧资源表单操作均指这些高级工具。

### 5.2 顶栏和账户

全局搜索支持当前网络或全部网络中的设备、设备组、共享和网络名称，`Ctrl/⌘ K`
打开，Escape 关闭。通知可标记已读；问题可标记已知，两者按账号、网络、对象及问题指纹保存。
凭据风险阶段或问题证据指纹变化后重新提示；标记已知不改变配置或消除故障。
点击设备组搜索结果会进入访问页面，并用 `source=group:…` 选中该组；即使该组不在当前候选列表中也能显示名称和权限，连续选择其他组会更新访问结果和链接中的来源。

语言和主题从右上角账户菜单调整，仅把偏好存入本地存储，刷新后保留；不保存邀请令牌、密钥或表单秘密。
移动端通过顶栏菜单打开侧栏。抽屉支持键盘焦点约束、Escape 关闭和焦点返回。
页面脚本加载完成前，顶栏按钮禁用，表单暂不可操作；加载完成后再接收点击和输入。

### 5.3 设备与共享详情

设备支持名称/位置搜索、在线/离线/停用及 Linux/Android 筛选，每页 50 项，数量由后端计算。
工具栏中的 **更多 → 导出当前结果** 会按当前筛选导出最多 10,000 条非秘密设备字段，并处理 CSV 公式前缀。
点击名称打开 **状态、共享与访问、维护**。默认“状态”只展示设备地址、系统、位置和当前连接解释；
网络名称、设备标识、完整标签、Presence 与凭据原始明细放在可展开的 **技术详情**。名称和位置从状态页的 **修改基本信息** 进入，
不会改变设备身份、设备网络地址或现有访问规则；凭据更新、退役和操作记录集中在“维护”，凭据序列等低频字段再折叠一层。

共享详情按 **状态、共享信息、谁可以访问、网关路径** 分层。“状态”固定区分 **配置、授权、连接、可达性**，缺失或过期观测显示“未知 / 未检查”；
“共享信息”直接编辑设备服务名称、协议、端口和 DNS；“谁可以访问”查看已有授权、添加设备或设备组授权，以及逐条撤销或恢复授权。暂停/恢复与普通设置分开；只有局域网资源与互联网出口显示“网关路径”；资源 ID、底层类型和原始数据在状态页的 **技术详情** 中按需展开。
设备和共享详情会把当前对象写入 URL 的 `resource` 参数：刷新页面仍会重新打开同一对象；从列表打开详情后，无论使用浏览器“返回”还是详情的关闭按钮，都会回到原列表并保留该次页面会话中的搜索、筛选和分页状态。直接通过详情链接打开时，关闭详情只移除 URL 中的 `resource`，不会把用户带离控制台。
详情中的 **重新检查** 重新获取并评估真实记录，不生成连通性证据。
TCP 探测成功仅证明网关到指定地址端口的连接，不代表应用认证、UDP 或完整互联网正常。

设备加入和共享创建现在按连续任务组织，不要求先理解底层资源模型：

- **添加设备**：在设备页打开四步弹窗：设备信息 → 接入方式 → 等待上线 → 完成。第二步可切换复制命令、扫码加入和手动输入，或下载加入文件；第三步检查真实加入申请并核对设备本机指纹，批准后可进入详情。第一步填写设备名称、设备平台和可选设备组；默认使用人工确认和 15 分钟有效期，其他加入方式与期限在邀请记录的高级表单设置。已签发邀请的设置不会在返回上一步时改变。
- **设备组**：设备页右上角点击“设备组”→“新建设备组”，填写名称、勾选成员并“保存设备组”。再次打开同名组可编辑成员。保存组本身不新增授权；在共享详情的“谁可以访问”中选择该组并预览、确认授权，或在“访问”页选择该组查看结果。受控标签匹配保留为折叠选项；需要资源集合时使用“访问 → 高级访问工具”。
- **添加共享**：在居中弹窗中按“共享类型 → 共享信息 → 谁可以访问 → 确认创建”四步完成。
  首步用卡片选择设备服务、局域网资源或互联网出口；返回上一步保留草稿，取消未保存修改需要确认。
  第二步直接填写名称、提供设备、协议/端口和可选 DNS；设备服务不需要“更多设置”。设备候选列表存在后续页时自动显示搜索和翻页；局域网与互联网出口的“更多设置”保留站点、DNS 解析地址、IPv6 出口、授权范围及可选操作原因。
  HTTP/HTTPS 是 TCP 服务预设，默认端口为 80/443，已手工修改的端口会保留。
  设备服务 DNS 填写别名（如 `nas`），完整域名由网络 DNS 设置生成；局域网单主机目标的 DNS 地址自动取目标地址，网段目标需要另填解析地址。
  第三步通过卡片选择当前网络真实的设备或设备组，默认不新增授权；原型中的示例组不会自动创建。
  最后一步展示真实后端预览，确认后才创建；网关转发仍需显式批准。创建后直接查看共享状态，
  或跳到“访问”页继续检查这个共享。访问页会保留共享上下文，避免再次从完整共享列表中查找。
- **设备 → 访问**：设备详情的“共享与访问”可继续进入完整访问页；当前设备以 `source=peer:…` 保留为来源，访问页显示当前来源并提供查看设备详情的入口。
- **共享详情内管理授权**：打开“谁可以访问”，查看此共享的已有授权并逐条撤销或恢复；选择设备或设备组、填写原因、预览并确认后新增授权。保存后列表立即更新，不需要重新创建共享。查看者只有授权列表，没有变更入口。
- **共享 → 访问**：共享详情的“检查访问”继续使用 `resource=…` 保留当前共享；访问页显示“正在检查这个共享”并可返回共享详情。手动切换来源时，`source` 同步更新到 URL，刷新后仍能恢复该来源。
- “暂不新增授权”只表示本次不创建新授权；既有策略仍然有效，默认拒绝也不会被关闭。

### 5.4 切换与一致性

切换网络清空选中资源、邀请秘密和旧页面状态；表单有未保存修改时提示丢弃。
同一网络内，详情对象和访问来源通过 URL 保留，便于刷新、复制链接和跨页面继续任务；列表搜索、筛选与页码仍属于当前页面会话状态，不保证在完整刷新后恢复。设备基本信息保存成功后可直接“返回状态”，共享设置提交后可直接“查看状态”，避免保存后停留在编辑表单里。

“问题与维护”现在把修复和恢复确认分开：设备、共享或凭据处理完成后，回到该页点击 **重新检查**，控制台会重新读取当前真实证据。若待处理事项消失，才说明当前证据已经恢复；如果仍然存在，就继续保留并按建议下一步处理。保存配置、重启客户端、请求续期或点击某个修复按钮本身都不会被当作“已恢复”。重新检查结果会明确显示“当前证据已恢复 / 先前事项不再出现 / 仍有事项需要处理”，避免管理员只能猜测操作是否真正生效。

“问题与维护”中的 **安装状态** 默认只显示“共享基础设施当前无待处理事项”。只有控制服务 / 中继主机 / 审计观测 / 备份回报真的需要人工介入时才展开安装级提醒，并把处理入口指向 **系统工具 → 系统维护**；详细采样仍可手动展开查看。
请求按网络上下文隔离，迟到响应不得覆盖新网络。写入带 CSRF（会话模式）和版本前置条件；
共享编辑期间刷新证据会保留未提交的草稿。版本冲突显示明确提示，需核对最新内容后重新编辑并预览，不能覆盖他人的新配置。共享与授权的复合提交使用请求标识和预览摘要，精确重试返回已保存结果。

### 5.5 刷新和分页

SSE 使用事件游标重连、去重和重放；游标过期重新建立快照。通知触发重新查询，
不直接作为设备健康证据。另每 30 秒刷新有时效的读模型。大列表有分页和缓存上限；
网络切换器和大列表继续提供搜索与分页；组数量仍受现有配置上限约束。
访问页面把来源设备和设备组合并为一个可搜索候选集，单次最多读取 50 个设备和 50 个设备组，不再显示来源分页按钮；选中来源后才查询并展示该来源对共享的最终结果。共享向导中的提供设备和授权来源仍按原有分页选择器工作。

## 6. 推荐的首次配置顺序

对于新 Mesh，建议按以下顺序操作：

1. 创建 Mesh，并再次核对地址 CIDR、网关、DNS 后缀和 MTU。
2. 在离线、受控环境中创建并由 Root 签署 Authority 证书。
3. 在控制台暂存 Authority，核对证书预览，再激活它。
4. 创建 Relay 控制面记录。
5. 在控制台外为 Relay 生成私钥；只把对应的 Noise 公钥用于凭据轮换。
6. 暂存并激活 Relay 凭据，完成 Relay 配置和凭据文件分发。
7. 创建一次性 Join Ticket，让 Linux/Android 客户端加入。
8. 为 Peer 和 Service 设计稳定标签。
9. 创建所需 Service。
10. 先校验策略，再用真实 Peer/Service 组合模拟，最后替换策略。
11. 在概览检查待处理事项、设备在线数和共享数量；只有出现安装级提醒时再进入系统维护。
12. 在操作记录页面确认上述操作的 actor、action、target 和 result。

不要在尚无可用 Authority 时创建 Join Ticket 或轮换 Relay 凭据；Control 会拒绝无法安全签发的操作。

## 7. 仪表盘

**概览**只保留两项常驻总览：设备在线数/总数、共享总数。待处理事项已经由顶部健康提示和事项区表达，不再重复做一张统计卡；待审批设备或凭据风险只在实际存在时额外提示，
避免长期占据一个状态卡。统计由后端对整个网络计算，不从当前一页列表推断。首次使用时按设备、共享、访问顺序提示；
常用操作压缩为添加设备、添加共享和调整访问三个入口，最近活动只展示最近几条。

待办包括离线设备、凭据风险、待审批申请、缺少有效网关路径、仍有效的 TCP 探测失败、
设备拒绝应用配置。每条不再只显示错误名称，而是固定回答四件事：**发生了什么、现在影响什么、建议先做什么、从哪里进入处理**。
设备和共享类问题的处理入口会直接带上 `resource` 打开对应对象；入网申请直接进入添加设备流程。凭据到期前标为“暂不影响使用”，
已经过期时则明确提示新的身份连接可能失败。预期策略拒绝仍不列为故障。

标记 **已知** 只会把当前证据指纹对应的提醒收起，不会修改配置、恢复连接或关闭安全检查；证据变化后会重新出现。
已知问题仍可在“问题与维护 → 已知/全部”中查看；概览的“需要处理”只统计尚未标记已知的事项。

网络拓扑从概览移到 **问题与维护 → 排障：网络拓扑**，默认折叠，保留 Relay 区域、骨干和 Presence 的现有观测。
它不显示集中收集的 Peer-to-Peer 直连边，也不等同于完整业务流量图。

## 8. 网格

所有网络以卡片显示在线设备／总设备、已配置共享和待处理数量，统计来自后端概览，
不是从当前页推算；不把“已配置共享”称为“可达共享”。每页最多 12 个网络，提供翻页和重试。
网络设置使用双栏布局：基本信息、设备条件、网络功能；高级参数和 DNS 配置默认折叠。
名称、DNS 后缀和离线授权时长通过“保存网络设置”提交，设备条件通过自己的确认与保存操作提交，
两者使用独立版本前置条件。发生冲突保留草稿，重新读取按钮明确丢弃该部分草稿。
网络 ID、地址范围、网关和 MTU 为只读；DNS、共享及授权提供真实配置入口。

### 8.1 创建 Mesh

仅 admin 可以创建 Mesh。

1. 打开 **所有网络**。
2. 点击 **＋ 新建网络**，打开居中的 **创建一个独立网络** 弹窗，填写 **网络名称** 和 **网络标识**（如 `office-mesh`）。
3. 标识使用 1–63 位英文字母、数字或连字符，大写会自动转为小写（如 `OPC-mesh` → `opc-mesh`），首尾不能为连字符；格式错误会在字段下方明确提示。标识在当前安装内唯一，创建后只读。既有网络没有可读标识时，设置中仍显示原 UUID，不修改其身份。
4. 点击 **创建并切换**，弹窗显示真实后台初始化进度；提交后字段锁定，不能重复创建。Relay 确认就绪后自动进入新网络概览，再添加设备。
5. 提交前点击 **取消**、关闭或按 Escape，有草稿时需确认丢弃。提交后关闭弹窗不会取消后台任务，可从网络卡片进入设置查看进度；请求失败保留输入，同样输入重试复用请求 ID，执行失败重试原任务。

网络标识是管理用的可读标识，与内部 UUID 和 DNS 后缀独立。创建通过同一事务保存网络、唯一标识、任务、审计与 outbox；新网络不会继承其他网络的设备、共享或访问权限。

所有 Mesh 共用安装时登记的 Relay 宿主和 TCP 7777/7778；增删不操作容器、镜像或宿主端口。网络自动分配从 `100.64.0.0/10` 选择不与已有 Mesh 重叠的 `/24`，网关使用首个主机地址，默认 deny。

任务失败可重试原任务，不更换身份。删除允许包含设备和资源的网格：确认后停止新加入，后台通知在线设备并清理；Relay 离线时显示等待清理。离线设备在收到签名删除通知前可能继续已有直连。

每个 Mesh 的加密恢复包存放在 Control 恢复卷；解密私钥由管理员离线保管。参见[部署与恢复手册](cloud-local-deployment-plan.zh-CN.md)。需要指定创建参数时，在旧 `/meshes` 入口展开 **高级：手动网络管理 → 高级：手动配置**；该表单同样执行完整的异步创建。

| 字段 | 默认值 | 要求和含义 |
| --- | --- | --- |
| 名称 | 空 | 必填，去除纯空白后不能为空，最多 128 个 UTF-8 字节 |
| 地址 CIDR | `10.240.0.0/24` | Mesh 的私有地址前缀；应使用 IPv4 私网，网关和保留地址必须位于其中 |
| 网关地址 | `10.240.0.1` | Mesh 内保留的 DNS/网关地址，必须属于地址 CIDR |
| DNS 后缀 | `mesh.peerward` | 必须可规范化为小写 IDNA ASCII，至少两段，最长 253 字节 |
| Mesh MTU | `1280` | `1280` 至 `9000` |
| 保留地址 | 空 | 逗号分隔，均须位于 CIDR 内，最多 4,096 项 |
| 默认策略 | `deny` | 没有规则命中时允许或拒绝新连接 |
| 地址隔离时间 | `60` 秒 | Peer 被禁用后，其地址保持隔离、不能立即重新分配的时间 |
| 凭据重叠时间 | `3600` 秒 | 新旧凭据切换时旧凭据可继续接受的上限，最大 604,800 秒（7 天） |

生产环境建议保持默认策略为 `deny`，再显式添加允许规则。

### 8.2 编辑 Mesh

operator 或 admin 可以编辑已有 Mesh：

1. 在 **所有网络** 卡片或侧栏进入目标网络的 **网络设置**。
2. 在 **基本信息** 中修改名称；需要修改 DNS 后缀时展开 **高级设置**。
3. 点击页首 **保存网络设置**，等待保存反馈。
4. 如遇版本冲突，可保留当前草稿核对，或点击 **重新读取最新设置** 丢弃该部分草稿并读取服务端版本。

operator 可以修改名称和 DNS 后缀；admin 还可以修改高级设置中的离线授权时长。地址 CIDR、网关、MTU、保留地址、默认策略、地址隔离时间和凭据重叠时间只读展示；默认访问策略通过 **访问 → 高级规则** 维护。

### 8.3 Mesh 修订号

列表中的常见 revision 字段表示不同签名状态族的当前版本：

- `policy_revision`：策略；
- `authority_revision`：Authority 生命周期；
- `directory_revision`：Peer 目录；
- `relay_revision`：Relay 目录/拓扑；
- `service_revision`：服务；
- `revocation_revision`：精确撤销集合。

这些数值用于判断分发状态是否前进，不应手工修改。

### 8.4 删除 Mesh

仅 admin 可以删除网格，包括已投入使用的网格。在该网络的 **网络设置 → 危险操作 → 删除网络** 中输入其已保存的完整名称并确认删除。后端核对名称与版本后返回异步任务，立即禁止新加入、签发和普通变更。

后台向在线设备发送签名终止记录，再关闭该网格的会话并清理在线私钥和业务数据。Relay 离线时保留“等待 Relay 清理”，重复删除返回同一任务；失败可重试。其他网格继续运行，容器和共享端口不随删除变化。

审计、签名终止记录和生命周期墓碑会保留。删除不可撤销，同名重建使用新 ID 和身份。离线设备未收到终止记录前，可能继续已有直连；删除不等待所有设备上线。

网格列表和选择器只展示尚未删除的网格。已完成的创建、删除任务不再作为网格卡片展示；创建中、删除中、等待 Relay 清理以及可重试失败仍会显示。隐藏历史记录不等于删除审计或生命周期墓碑。


API：`DELETE /api/v1/meshes/{mesh_id}`，携带当前 `If-Match` 和 JSON `{"confirmation_name":"完整名称"}`；需要 `trust_manage` 权限及适用的 CSRF 校验，接受任务后返回 `202`。若服务端提示依赖或版本冲突，应先查看原因并刷新资源，不能通过更改前端按钮状态绕过检查。

全新安装按顺序执行仓库内全部数据库迁移。迁移 `0012_mesh_history_retention` 让历史审计及事件中的网格 ID 可以在网格删除后继续保留，不修改审计内容或移除其不可变保护；这不表示新版本支持从旧产品序列升级。版本兼容边界见[版本管理](versioning.md)。

## 9. 授权机构

当前界面的入口为 **系统工具 → 凭据与签发机构**。该功能仍用于证书轮换、到期处理与撤销；日常创建网格和设备入网无需打开它。收起导航不会移除 Mesh 的独立信任根或签发功能。

### 9.1 前置安全要求

- Root 私钥必须离线保存，不能上传到 Web 控制台。
- 上传的是 Root 已签署的 Authority 公钥证书，不是私钥。
- 暂存前核对证书的 Mesh ID、序列号和有效期。
- 轮换时应先暂存新 Authority，再完成分发和验证，最后激活并按计划撤销旧 Authority。

### 9.2 支持的证书文件

控制台支持两种输入：

1. 精确 144 字节的二进制 Authority 证书；
2. 不超过 8 KiB 的严格 TOML 文档。

TOML 证书必须只包含以下字段，未知字段会导致拒绝：

```toml
schema_version = 1
mesh_id = "<mesh-uuid>"
serial = "<credential-serial-uuid>"
public_key = "<64 个十六进制字符>"
not_before = 0
not_after = 0
signature = "<128 个十六进制字符>"
```

其中 `not_before` 和 `not_after` 是 Unix 秒，且 `not_before < not_after`。

### 9.3 暂存 Authority

1. 打开 **授权机构**，选择目标 Mesh。
2. 点击 **授权机构证书文件**，选择 `.cert`、二进制或受支持的文本证书。
3. 查看 **证书解析预览**：文件名、Mesh ID、凭据序列号、生效时间、到期时间。
4. 确认预览中的 Mesh ID 与当前 Mesh 完全一致。
5. 若这是轮换，可填写 **被替换的授权机构 ID**。这里需要 Authority 资源 ID，不是证书序列号。
6. 点击 **暂存授权机构**。

也可以展开 **高级：规范 base64url 证书值**，直接粘贴无填充的 base64url 证书，但文件导入更容易核对。

Control 会再次验证证书格式、当前有效期、Mesh 绑定和 Root 签名。浏览器解析成功不代表服务端一定接受。

### 9.4 激活 Authority

1. 在 **资源** 中选择已暂存 Authority。
2. 查看列表中的 `lifecycle`、`not_before`、`not_after` 和 `replacement_id`。
3. 在确认框中输入该 Authority 的完整**证书序列号**。Authority 下拉框显示的名称即序列号。
4. 点击 **激活授权机构**。
5. 等待列表刷新并确认 `lifecycle` 变为 `active`。

不要在新 Authority 的签发私钥尚未安全配置到 Control、证书尚未完成分发时激活它，否则新的 Join 或凭据轮换可能失败。

### 9.5 撤销 Authority

1. 选择目标 Authority。
2. 输入完整证书序列号。
3. 点击 **禁用或撤销所选资源**。
4. 确认 `lifecycle` 变为 `revoked`。

撤销会改变 Mesh 信任状态。撤销当前 Authority 前，必须确认替代 Authority 已激活、签发材料已配置、依赖它签发的凭据已完成轮换。Authority 生命周期转换还会受到服务端状态机约束；不合法的转换不会生效。

## 10. Peer 与凭据

### 10.1 理解 Peer 状态

Peer API 状态和操作表单涉及以下字段：

| 字段 | 含义 |
| --- | --- |
| `version` | 当前资源版本 |
| `name` | 用于网络标识的 DNS 安全名称 |
| `display_name` | 管理员填写的设备显示名称，支持中文；为空时显示网络名称 |
| `location` | 管理员填写的位置，如“家中书房”；为空时显示“未设置” |
| `mesh_addresses` | 实际分配给该 Peer 的 Mesh IP；离线时仍保留，不包含已释放或隔离的地址 |
| `labels` | 用于策略选择的完整标签集合 |
| `administrative_state` | `enabled` 或 `disabled` |
| `online` | Peer、Relay、Presence/运行时租约均有效时才为 true |
| `presence` | 当前主/备用 Relay、generation 和租约截止时间 |
| `credentials.active` | 当前凭据 |
| `credentials.pending` | 等待激活的凭据 |
| `credentials.overlap` | 有界重叠期内仍被接受的旧凭据 |

显示名称与位置独立于网络名称和策略标签，修改它们不改变 Peer ID 或地址。位置不通过公网 IP 推测，也不是 GPS 定位；系统与型号取自客户端上报的 `platform`、`platform_version`、`device_model` 标签，缺失时显示“未上报”。设备详情默认先回答“这台设备现在是什么状态”，再按 **共享与访问 → 维护** 进入具体任务；名称和位置通过状态页的小入口修改，操作记录放在维护页折叠区。网络名称、标识、完整标签、Presence 和凭据原始明细统一收进状态页的可展开技术详情，避免普通运维时先面对工程字段。

设备详情字段由建库迁移链中的 `0016_peer_device_details` 提供；全新安装执行完整迁移链，不应挑选单个迁移。未设置的显示名称、位置留空，地址从实际分配记录读取。

从仪表盘点击 Relay 进入本页时，页面 URL 会带 `relay_id`，此时列表只显示当前附着到该 Relay 的 Peer。若要恢复普通 Peer 列表，可从左侧重新进入该页面，或移除该过滤参数后重新打开。

### 10.2 添加设备

在 **设备 → 添加设备** 创建一次性邀请，再在 Linux 客户端使用命令或用 Android 扫码。
默认需要管理员审批，审批后继续检查设备是否真正上线。完整流程见第 12 节。

网络名称为 1–63 个 ASCII 字符，只能包含字母、数字和连字符，首尾必须为字母或数字。
显示名称可以使用中文。设备在本地生成并保管私钥；只创建控制面记录不代表完成入网。
直接创建无凭据 Peer 记录仍是 API 能力，不再作为日常添加设备按钮。

### 10.3 编辑 Peer

点击设备打开详情抽屉，在 **状态 → 修改基本信息** 中编辑显示名称和位置，再点击 **保存更改**。
未保存时关闭、切换页签或切换网络会提醒；保存不会改变网络名称、地址或策略标签。

修改网络名称、完整标签或管理状态，打开页面底部的 **高级设备工具**，
选择资源后点击 **编辑所选资源**。标签是完整替换，删除标签可能改变策略匹配结果。

### 10.4 Peer 凭据生命周期

选择 Peer 后，**凭据序列号**下拉框会列出当前 `pending`、`active` 和 `overlap` 凭据。存在 pending 时通常会优先选中它；执行操作前必须再次核对生命周期和完整序列号。

设备详情 → **维护 → 发起更新请求** 可提交原因与期限（1 小时、24 小时或 7 天）。
请求绑定网络、设备、当前凭据及唯一标识，由在线签发材料签名，经 Relay 发送；
设备在本机生成新密钥，复用 Linux/Android 的持久化轮换和崩溃恢复流程。
控制台和后端不生成、接收或保存设备私钥。旧客户端显示“需升级”，离线设备显示等待。
请求状态依次可能为已提交、已投递、正在更新、已激活等待重新连接、已完成；
仅替代凭据完成可信重新认证后显示完成。期限届满可重新发起；当前凭据已过期时使用现有本地恢复流程。

凭据更新完成与业务可达性分别判断。Linux/Android 重启或从系统休眠恢复后，
会拒绝复用已经失去单调时钟有效期的旧授权；设备通过签名的配置回执请求新租约，
Control 合并同一租约的请求并重新签发，保持原配置和授权范围。Android 只有在当前凭据、
设备准入、完整签名状态和有效租约均可用时才显示健康；等待新授权期间继续阻断数据。

高级凭据管理仍可查看 pending、active、overlap 和 revoked。设备发起轮换并出现 pending 凭据后：

- 点击 **激活凭据序列号**，将待处理凭据变为 active；
- 点击 **撤销凭据序列号**，精确撤销所选 serial。

撤销 active 凭据会使该 Peer 无法继续用它认证。凭据激活和撤销均要求输入完整资源名称；同时核对选中的凭据序列号。

### 10.5 禁用 Peer

日常退役使用设备详情的 **维护 → 退役设备**，填写完整网络名称和原因并确认。
下述高级禁用入口继续保留。

这是高风险、不可当作普通编辑回滚的操作：

1. 选择 Peer。
2. 阅读影响提示。
3. 在确认框输入完整 Peer 名称，大小写和字符必须完全一致。
4. 点击 **禁用或撤销所选资源**。

成功后，Control 会在同一变更中：

- 将 Peer 的管理状态设为 disabled；
- 撤销该 Peer 的所有未撤销凭据；
- 禁用该 Peer 发布的所有 Service；
- 删除当前主/备用 Relay Presence；
- 释放地址并进入 Mesh 配置的隔离期；
- 推进 directory、service 和 revocation revision。

资源行仍会保留用于审计和状态查看；该按钮不是物理删除。

### 10.6 删除已退役 Peer

1. 选择 Peer，按上一节操作先禁用；已禁用的 Peer 可直接继续。
2. 在 **输入完整资源名称** 中重新输入所选 Peer 的完整名称。
3. 点击 **删除所选 Peer**。

删除按钮只对已经保存为禁用状态的 Peer 开放；仅修改管理状态下拉框而未保存不会启用该按钮。删除成功后，资源选择和编辑表单清空，该 Peer 从列表及拓扑中移除。

删除采用数据库已预留的 `deleted` 状态，保留 Peer 记录、原有引用和审计历史，并记录 `peer.delete` 审计事件。删除时再次撤销剩余凭据、禁用服务、清理主/备用 Relay Presence 和当前健康状态、隔离地址，并取消未完成的凭据轮换。已删除 Peer 无法重新启用；同名设备再次加入时会获得新的 Peer 身份。

API：`POST /api/v1/meshes/{mesh_id}/peers/{peer_id}/delete`，携带当前 `If-Match` 和 JSON `{"name":"完整名称"}`。要求 `resource_write` 权限和适用的 CSRF 校验。未禁用返回 `409 peer_must_be_disabled`，名称不一致返回 `400 confirmation_mismatch`，版本过期返回 `409 revision_conflict`。原 `DELETE /api/v1/meshes/{mesh_id}/peers/{peer_id}` 继续表示禁用，以兼容现有客户端。

## 11. Relay

### 11.1 创建 Relay 记录

1. 选择目标 Mesh。
2. 填写 Relay 名称。
3. 填写一个或多个 **Peer 端点**。
4. 填写一个或多个 **骨干端点**。
5. 点击 **创建**。

示例：

```text
Peer 端点：tcp://relay.example.com:7777, tcp://203.0.113.10:7777
骨干端点：tcp://relay.example.com:7778, tcp://203.0.113.10:7778
```

字段约束：

| 字段 | 要求 |
| --- | --- |
| 名称 | 非空，最多 128 个 UTF-8 字节 |
| Peer 端点 | 1 至 16 个、逗号分隔、不可重复的规范 `tcp://host:port` URI |
| 骨干端点 | 1 至 16 个、逗号分隔、不可重复的规范 `tcp://host:port` URI |
| host | 有效 IP 或 ASCII DNS 名；不能是 unspecified/multicast IP |
| port | 非 0 TCP 端口 |

URI 不允许用户名、密码、查询参数或片段。IPv6 地址需使用方括号，例如 `tcp://[2001:db8::10]:7777`。

Web 表单支持区域和路由权重，默认值分别为 `default` 和 `100`。权重合法范围是 1 至 1000，区域是最长 32 字节的小写 DNS 风格标签。

### 11.2 编辑 Relay

1. 选择 Relay。
2. 修改名称、Peer 端点、骨干端点或管理状态。
3. 点击 **编辑所选资源**。

端点字段是完整列表替换。保存前确认没有漏掉仍需使用的端点。表单也可编辑 Relay 区域和路由权重：区域使用至多 32 字节的小写 DNS 标签，权重范围为 1–1000。

### 11.3 轮换 Relay 凭据

Relay 私钥必须在 Relay 主机或受控密钥环境中生成，私钥绝不能粘贴到控制台。

1. 在控制台外生成新的 X25519/Noise 密钥对。
2. 选择 Relay。
3. 在 **新 Noise 公钥**中输入 32 字节公钥的 64 个十六进制字符。
4. 点击 **轮换凭据**。
5. 等待 `credentials.pending` 出现新的 serial。
6. 将与该公钥对应的私钥和所需凭据材料按部署流程安全安装到 Relay。
7. 由 admin 在 **凭据序列号**中选中 pending serial。
8. 点击 **激活凭据序列号**。
9. 确认 Relay 能用新凭据上线，且新 serial 为 active。
10. 经过计划的重叠窗口后，选择旧 overlap serial 并点击 **撤销凭据序列号**。

创建 Relay 记录或提交公钥都不会在浏览器内生成、下载或备份私钥。没有当前有效 Authority，或 Control 未配置该 Authority 的在线签名材料时，轮换会失败。

### 11.4 禁用 Relay

1. 评估 Peer 是否已有其他可用 Relay，避免全 Mesh 失联。
2. 选择 Relay。
3. 输入完整 Relay 名称。
4. 点击 **禁用或撤销所选资源**。

成功后将禁用 Relay、撤销其全部凭据、清除关联 Presence，并推进 relay、directory 和 revocation revision。资源记录仍会保留。先扩容并验证替代 Relay，再禁用生产 Relay。

## 12. 加入凭证

### 12.1 创建一次性 Join Ticket

1. 在目标网络点击 **添加设备**，填写设备名称（支持中文），选择平台（Linux、Android），按需勾选一个或多个设备组。默认不分组；选中后可查看这些组已有的共享授权。
2. 点击“下一步”保存本次邀请的设备信息，生成需人工批准、15 分钟有效的一次性邀请。留空名称时使用“新设备”。
3. 在“接入方式”选择复制命令、扫码加入或手动输入。Linux 使用 `peerward join accept --bundle-file - --output-dir ./peerward-device` 从标准输入提供邀请链接；也可下载 `peerward-join.txt` 后使用 `--bundle-file ./peerward-join.txt`。选择 Android 时默认打开扫码页，可扫描真实邀请二维码；Linux 默认打开命令页，仍可手动切换。页面显示实际到期时间，不能在签发后更改有效期。
4. 点击“我已在设备上操作”进入第三步，再“检查连接”。需要审批时，通过可信渠道核对完整身份指纹，再批准。
5. 进入设备页确认实际在线；批准成功不代表客户端已连接。

设备名称最多 128 个字符，提交时去除首尾空白，保留中文、大小写和内部空格。名称与用途保存在邀请中，并在实际入网事务中写入设备，即使控制台关闭也不会丢失。用途是说明信息，与策略标签分开保存，不授予权限；加入后可在设备详情的基本信息中修改名称、用途和位置。网络名称仍由设备接入过程生成。

平台选项决定接入指引，不覆盖设备实际报告的系统信息。已签发邀请返回上一步时只读，避免展示内容与已签发邀请不一致。

需要固定 DNS 网络名称、持邀请直接加入、预绑定指纹、控制标签、临时/定期设备或其他期限时，关闭弹窗，展开“邀请记录与高级选项”使用高级邀请表单。网络名称仍要求 1–63 位小写英文字母、数字或短横线，且首尾不能为短横线。
邀请链接、二维码只在本页内存显示一次，切换网络或刷新后清除；后台列表不返回令牌。
bundle 包含 claim URL、Root 指纹、到期时间、随机 nonce 和 Mesh ID。

### 12.2 安全处理要求

- Join 链接是短期秘密，只发送给预期设备和人员；
- 不要把链接写入工单、截图、终端历史、代理日志或群聊；
- 控制台只在创建后的浏览器内存中保留链接，刷新或离开后无法恢复；
- 丢失链接时取消原 Ticket 并创建新的，不要尝试从数据库或日志恢复 token；
- 客户端认领前会校验 Root 指纹、有效期和 Wire major 5 支持。

创建要求当前 Mesh 存在有效 active Authority，且 Control 配置了对应签发材料。否则可能返回 `active_authority_unavailable` 或 `active_authority_key_unavailable`。

### 12.3 查看和取消 Ticket

列表只显示非取消的 Ticket 元数据：

- `expires_at`：到期时间；
- `consumed`：是否已成功认领；
- `version`：资源版本。

取消未使用 Ticket：

1. 在资源下拉框选择 Ticket。
2. 点击 **禁用或撤销所选资源**。

该操作要求输入所选 Ticket 的完整显示名称确认。成功后 Ticket 从当前列表消失，之后不能被认领。已消费 Ticket 也不能再次用于不同的认领内容。

## 13. 策略

默认页面先选择一台设备或一个设备组，再显示这个来源对共享资源的 **访问结果**，不再先铺开整张权限矩阵。
来源候选可搜索，单次最多读取 50 个设备和 50 个设备组；资源仍可搜索和分页。每个结果由后端策略求值，
点击 **查看原因** 进入该来源与资源的自然语言解释。设备组复用 Collections，
成员变化会更新派生授权。服务使用服务策略求值器；网段和出口需指定目标地址、协议、端口、网关后判断。
组内结果不一致显示“部分允许”，缺少条件或地址证据不推断允许。
访问详情直接显示命中规则及原因、添加授权；服务、局域网资源和互联网出口的简易授权均可逐条撤销和恢复。
简易授权只追加或修改对应规则，保留原顺序、拒绝及高级条件。多条允许规则可能叠加，撤销一条后需重新模拟。
撤销或恢复前会显示资源、来源和重叠目标，填写原因并确认后提交。后台校验版本、现有策略测试和权限；冲突或测试失败时不应用修改。
网段和出口只允许在此直接切换单个来源设备或设备组、单个资源的简单允许规则；多对象、拒绝、网关限制、有效期、标签、CIDR 或复杂端口范围均显示“高级规则”，通过对应入口修改。
复杂网段规则的修改、删除、条件、测试和历史恢复在默认折叠的高级区域中完成。

**高级：模拟具体条件** 可选择已配置的 TCP/UDP 协议和发布设备的网络地址，端口取服务当前配置。地址和协议留空时汇总现有地址族和协议；结果不一致显示“部分允许”。指定地址必须属于发布设备，不能用任意外部地址代替。模拟只解释策略，不会建立网络连接，也不能代替可达性证据。

### 13.1 操作前必须了解的行为

在访问页点击 **配置设备互通**，或页面底部的 **高级访问工具**，打开同一个访问规则编辑器。
编辑器自动读取完整的已保存策略，保留已有规则和默认动作；无需复制 JSON 或手动递增版本号。

日常操作按以下顺序完成：

1. 按名称选择 **发起设备** 和 **目标设备**，可搜索和翻页查找更多设备。
2. 选择 **允许的通信**：Ping、SSH、HTTP 或 HTTPS，再选择单向或双向。Ping 默认双向，自动生成两条不带端口的 ICMP 规则。
3. 点击固定在抽屉底部的 **保存规则**。系统先校验，再用当前已加载版本加一提交；显示“规则已保存”后才表示提交成功。

需要一次配置多组设备时，可先点击 **加入待保存规则**，核对规则摘要后继续选择下一组，最后统一保存。
单组设备不需要这一步；选择完成即可直接保存。

**仅校验**不保存。规则按原有优先级执行，快捷添加不会覆盖已有规则或绕过更高优先级的拒绝规则。
**高级规则编辑**保留自定义协议、端口、CIDR、标签、优先级与 JSON 编辑；**资源规则与设备组**收纳原有资源策略和设备组工具。

保存仍是整份策略的原子提交。后台刷新不会覆盖未保存草稿；出现版本冲突会停止保存并保留草稿。
点击 **重新加载** 后，需要明确选择 **放弃并重新加载** 才会丢弃当前草稿。关闭抽屉或切换网络时也会提示未保存内容。
保存成功只证明规则已提交，设备是否连通仍需在设备上实际测试。

### 13.2 策略求值模型

- 数字较小的 `priority` 先求值；
- 同一 priority 下，`deny` 先于 `allow`；
- action 也相同时按规则 UUID 排序；
- 只考虑 `enabled=true` 的规则；
- 第一条完整匹配的规则决定结果；
- 没有规则命中时使用 `default_action`；
- source/destination 内部：Peer ID 列表和 CIDR 列表各自表示备选项，标签表示必须同时满足的键值对；不同选择维度组合使用约束匹配；
- 空 Peer、标签或 CIDR 选择器表示该维度不设限制；
- TCP/UDP 的空端口列表表示所有端口；
- `any` 和 `icmp` 不能带目标端口范围。

### 13.3 使用规则卡编辑

点击 **添加规则**会生成：

- 新 UUID；
- 按当前规则数生成的 10、20、30……priority；
- `deny`；
- enabled；
- 不记录命中日志；
- 空 source/destination；
- `any` 协议；
- 空端口范围。

规则卡字段：

| 字段 | 输入格式 |
| --- | --- |
| 启用 | 是否参与求值 |
| 动作 | allow 或 deny |
| 优先级 | 0 至 4,294,967,295；数字越小越先匹配 |
| 来源 Peer | 逗号分隔的 Peer UUID |
| 来源标签 | `key=value`，多个值逗号分隔 |
| 来源 CIDR | 逗号分隔 CIDR |
| 目标 Peer | 逗号分隔的 Peer UUID |
| 目标标签 | `key=value`，多个值逗号分隔 |
| 目标 CIDR | 逗号分隔 CIDR |
| 协议 | Any、TCP、UDP、ICMP |
| 目标端口 | 如 `80, 443-445`；端口不能为 0，范围起点不能大于终点 |
| 记录命中决策 | 命中时请求生成有界结构化决策记录 |

> **规则排序提示：** 规则卡直接编辑真实优先级。实际求值按优先级、拒绝优先、UUID 排序，与卡片显示位置无关。修改后先验证并模拟，再发布；其他高级条件保持原样。

### 13.4 高级 JSON

展开 **高级 JSON 导入/导出**可以编辑完整 `rules` 数组。示例：

```json
[
  {
    "id": "11111111-1111-4111-8111-111111111111",
    "priority": 100,
    "action": "allow",
    "enabled": true,
    "log": true,
    "source": {
      "peer_ids": [],
      "labels": { "team": "platform" },
      "cidrs": []
    },
    "destination": {
      "peer_ids": [],
      "labels": { "role": "server" },
      "cidrs": []
    },
    "protocol": "tcp",
    "destination_ports": [
      { "first": 443, "last": 443 }
    ]
  }
]
```

上述 source/destination 标签匹配的是 Peer 标签；示例要求目标 Service 的发布 Peer 具有 `role=server`。当前策略模拟用 Service 找到发布 Peer 和端口，再以发布 Peer 的 ID、地址和标签执行目标选择器。不要假设仅给 Service 本身添加同名标签就一定会命中目标规则。

主要上限：

- 每份策略最多 1,024 条规则；
- 每个选择器最多 1,024 个 Peer ID；
- 每个选择器最多 64 个标签；
- 每个选择器最多 256 个 CIDR；
- 每条规则最多 256 个端口范围；
- 规则 ID 不可重复；
- Peer ID 和 CIDR 列表内部不可重复。

### 13.5 校验策略

1. 在访问规则编辑器中修改规则；版本号由系统自动管理。
2. 必要时在高级规则编辑中调整 default action。
3. 点击底部 **仅校验**。
4. 查看结果：

   - 有效时显示规范策略的 SHA-256；
   - 无效时显示字段路径和原因；
   - `default_allow_permits_unmatched_initiations` 表示默认允许未匹配连接；
   - `no_enabled_rules` 表示没有启用规则。

校验无副作用，不会保存策略。校验返回的规范化结果不会自动覆盖编辑器内容。

### 13.6 模拟访问

1. 输入或从浏览器建议列表选择 **源 Peer UUID**。
2. 输入或选择 **目标 Service UUID**。
3. 选择 TCP 或 UDP。
4. viewer 只能选择当前已保存策略；operator/admin 可选择当前策略或未保存草稿。
5. 点击 **模拟访问**。

结果包含：

- `ALLOW` 或 `DENY`；
- 实际 action；
- 命中的规则 UUID，或 `default`；
- 规范策略 SHA-256。

模拟使用真实 Peer、Service 和生产策略求值器，但不会建立网络连接，也不会修改资源。

### 13.7 保存规则

推荐顺序：

1. 打开 **配置设备互通**，等待已保存规则加载完成。
2. 完成设备选择或高级规则编辑，核对新增规则及已有规则。
3. 点击底部 **保存规则**；系统自动校验并递增版本，失败时显示原因且保留草稿。
4. 确认“规则已保存”，需要时重新打开抽屉核对持久化结果。
5. 在审计页面确认 `policy.replace` 成功，并从实际设备验证允许与拒绝的通信。

策略替换会推进 policy 和 directory revision。不要仅凭页面显示顺序判断实际优先级。

## 14. 服务

共享页统一管理三类资源：设备服务使用 Service，局域网使用 NetworkResource + GatewayBinding，
互联网出口使用同一资源模型的 Internet 目标。**添加共享**向导选择提供设备、目标、可选访问来源，
高级区可填写 DNS、站点和原因。先预览受影响设备数、重叠目标，再确认；资源、绑定、DNS、授权在同一事务保存。
同一提供设备只能绑定一个互联网出口；已有出口时编辑该出口，或选择其他提供设备。不同站点的目标地址不能产生歧义；同一局域网的重叠资源应使用相同站点标识，并核对预览中的影响。

共享详情默认打开 **状态**，先看配置、授权、路径、可达性四层证据；常规修改统一进入 **共享信息**，避免状态信息和表单混在同一屏。
设备服务可在“共享信息”修改服务名称、DNS、协议和端口；提供设备和共享类型在创建后固定，更换需新建共享。修改会重新计算此服务的派生授权。局域网或出口在“共享信息”中点击 **修改目标**，通过 **编辑共享目标** 可修改名称、目标地址/地址族及可选 TCP 探测。填写原因，预览变更前后的目标、探测和影响，再输入原名称提交。
修改目标会撤回原路径并清除现有网关批准，包括自动批准资格；访问规则、标签和 DNS 记录保留，需自行核对仍指向旧地址的 DNS。
局域网或出口的 **网关路径** 中可管理当前提供网关的优先级、批准或撤回目标；普通设备服务不显示该页签。新增多个网关、站点标识和自动批准规则继续使用页面底部 **高级共享工具** 中的底层资源表单。底层资源 ID、版本、类型和原始 JSON 收进状态页的 **技术详情**，不再占一个顶层页签。
**暂停共享**从“共享信息”中的独立危险操作区进入，输入共享名称、原因并核对重叠共享；
暂停保留共享设置及授权，通过访问规则和撤回路径阻止访问。恢复重新校验条件并复用原授权。
暂停/恢复提交后继续检查实际路径与设备回执，离线设备不会被显示为已应用。

下列为保留的高级 Service 表单说明。


### 14.1 创建 Service

1. 选择目标 Mesh。
2. 在 **发布 Peer ID**中输入或从建议列表选择已存在 Peer。
3. 选择协议：TCP、UDP 或 TCP + UDP。
4. 输入 **网格公开监听端口**。
5. 可选填写 DNS 别名。
6. 填写 Service 标签。
7. 点击 **创建**。

字段约束：

| 字段 | 要求 |
| --- | --- |
| 发布 Peer | 当前 Mesh 中存在的 Peer UUID |
| 协议 | TCP、UDP 或同时发布两者 |
| 监听端口 | 1 至 65535 |
| DNS 别名 | 可选，1 至 63 个 ASCII 字符，只允许字母、数字和连字符，首尾不能是连字符 |
| 标签 | 与 Peer 标签相同：最多 64 项，`key=value`、逗号分隔 |

共享列表优先显示显示名称，其次为 DNS 别名；两者都没有时显示端口号。同一个 Service 可以同时发布 TCP 和 UDP。访问详情可分别模拟，也可汇总比较；保留的高级策略模拟表单一次测试一个协议。

当前 Service 标签会随服务资源保存和发布；但当前规范策略求值器的 source/destination 标签选择器直接匹配 Peer 标签。要按标签控制服务访问，应把规则所需标签配置到发布 Peer，并同时使用协议和目标端口约束；不要只依赖 Service 标签。

### 14.2 禁用 Service

1. 选择 Service。
2. 点击 **禁用或撤销所选资源**。
3. 输入完整资源名称后确认，等待 `state` 变为 `disabled`。

服务详情提供可恢复的暂停和名称/DNS 编辑。高级 **禁用 Service** 是原有不可恢复禁用路径；日常维护请使用详情中的暂停。

禁用 Peer 会级联禁用该 Peer 发布的全部 Service。

## 15. 批量操作

Peer、Relay、Join Ticket 和 Service 页面支持同类资源批量操作；Authority 不支持批量操作。没有已加载资源时不显示批量操作。

“添加设备”页面的 **批量取消邀请** 位于默认折叠的 **邀请记录与高级选项** 中，用来一次作废多张不再使用的邀请。它不负责批量添加或审批设备，也不会移除已加入的设备；入网申请仍需逐台核对身份。

### 15.1 影响范围

| 当前页面 | 批量结果 |
| --- | --- |
| Peer | 禁用 Peer、撤销凭据、禁用其 Service、清除 Presence、隔离地址 |
| Relay | 禁用 Relay、撤销凭据、清除 Presence |
| Join Ticket | 取消仍为 active 的 Ticket |
| Service | 禁用仍为 enabled 的 Service |

### 15.2 执行步骤

1. 展开页面相应高级区域，在 **批量操作** 中勾选 1 至 100 个当前页资源；邀请管理使用 **邀请记录与高级选项 → 批量取消邀请**。
2. 点击 **预览批量操作**（邀请管理为 **预览取消邀请**）。
3. 查看每一项的 ID、当前状态和 `就绪`/错误码。
4. 只有全部项目都就绪时，才会显示提交确认区。
5. 输入完整 Mesh 名称。
6. 输入所选项目数量。
7. 点击 **提交批量操作**（邀请管理为 **确认取消所选邀请**）。
8. 等待 `批量操作已提交: <数量>`。

预览会捕获每个资源的精确 version。提交时 Control 会排序并锁定全部资源，再重新核对 version 和状态。任一资源发生变化、被其他管理员操作或进入不允许状态，整批都会回滚，不会产生部分成功。

修改勾选项后，旧预览和确认输入会被清空，必须重新预览。批量选择只覆盖当前已加载资源；跨页资源需要先加载，且总数仍不能超过 100。

## 16. 审计

审计页面只展示元数据，不保存请求正文、Ticket、Cookie、私钥或业务载荷。

常见字段：

| 字段 | 含义 |
| --- | --- |
| `actor` | 发起操作的 OIDC subject 或开发身份 |
| `action` | 稳定操作名，例如 `peer.create`、`peer.disable`、`policy.replace` |
| `target_type` | 目标资源类型 |
| `target_id` | 目标 UUID；批量/策略类操作可能为空 |
| `timestamp` | RFC 3339 发生时间 |
| `result` | `success`、`denied` 或 `failure` |
| `metadata` | 已清理的非秘密元数据 |

审计按时间倒序分页。具有 `resource_read` 的用户若当前 URL 带已选择的有效 `mesh` 参数，会看到该 Mesh 的审计；未选择 Mesh 时显示全局审计。auditor 不能通过当前 Web 界面列出和选定 Mesh，因此通常看到全局审计。

调查操作：

1. 记录异常资源 ID、事件时间和页面错误的 request ID。
2. 在审计中查找对应 action、target ID 和 actor。
3. 判断结果是 success、denied 还是 failure。
4. 将 request ID 与 Console、Control 的结构化日志及 `traceparent` 关联。
5. 不要把“列表为空”解释为没有事件，也可能是角色、Mesh 范围或分页问题。

## 17. 高风险操作检查表

执行 Authority 激活/撤销、凭据撤销、Peer/Relay 禁用、策略替换或批量操作前，至少确认：

- 当前页面和目标 Mesh 正确；
- 当前角色具备服务端要求的能力；
- 资源 ID、名称、serial 和 version 来自最新页面；
- 已评估对在线 Peer、Relay、Service 和管理通道的影响；
- 存在经过验证的替代 Authority、Relay、凭据或策略路径；
- 已保留必要的非秘密回退信息；
- 操作窗口、负责人和审计时间已记录；
- Join 链接、私钥、Cookie、Bearer 和 CSRF 没有进入记录；
- 操作后会检查资源状态、拓扑、审计和外部监控。

## 18. 常见错误与处理

控制台错误区域会显示稳定错误码、安全消息、字段错误和 `Request <UUID>`。排障时优先保存 request ID，不要只截图提示文字。

| 错误码/现象 | 常见原因 | 处理方式 |
| --- | --- | --- |
| `missing_credentials` | 未登录或请求没有开发 Bearer | 使用 OIDC 登录；检查 Console/Control 鉴权配置 |
| `invalid_session` | 会话过期或被撤销 | 重新登录 |
| `insufficient_role` | 当前账号缺少能力 | 核对页面角色和 IdP 组映射；Relay 凭据激活/撤销需 admin |
| `csrf_required` / `csrf_invalid` | Cookie 会话的 CSRF 值缺失或过期 | 刷新页面并重新登录；检查反向代理是否正确转发 Cookie/头 |
| `control_unavailable` | Console 无法连接 Control | 检查 Control 进程、`PEERWARD_CONTROL_URL`、网络和 readiness |
| `invalid_control_response` | 表单无法转换为合法类型，或上游返回不符合契约 | 检查数字、UUID、JSON、逗号列表和 `key=value` 格式 |
| `control_response_too_large` | Control 响应超过 Console 安全上限 | 缩小查询范围；检查异常上游响应 |
| `invalid_name` | 名称为空、过长或不符合 Peer DNS 标签规则 | 按对应页面字段规则修改 |
| `invalid_labels` | 标签缺 `=`、键值为空或超限 | 改为合法的逗号分隔 `key=value` |
| `invalid_peer_endpoints` / `invalid_backbone_endpoints` | Relay 端点为空、重复、超过 16 项或 URI 非规范 | 使用唯一的 `tcp://host:nonzero-port` |
| `invalid_expiry` | Join Ticket 有效期不在 60 秒至 7 天 | 修改有效期 |
| `active_authority_unavailable` | 当前没有有效 active Authority | 暂存并激活有效 Authority |
| `active_authority_key_unavailable` / `authority_signer_unavailable` | Control 没有对应 Authority 的在线签名材料 | 修正 Control `join_issuers`/密钥挂载，不要上传私钥到网页 |
| `invalid_authority` | 证书格式、有效期、Mesh 绑定或 Root 签名不正确 | 回到离线签署流程重新核验 |
| `revision_conflict` | 页面资源 version 已过期 | 刷新页面、重新选择资源、核对变更后重试 |
| `confirmation_mismatch` | 删除确认名称与已保存名称不完全一致 | 重新输入完整名称，保留大小写和空格 |
| `mesh_not_active` | 网格正在创建或删除 | 查看生命周期任务；就绪前无法加入，删除后无法变更 |
| `mesh_not_managed` | 网格没有动态生命周期身份 | 新建受管理网格；不迁移旧身份 |
| `revision_rollback` | 新策略 revision 不大于当前值 | 读取当前 revision，使用严格更大的正整数 |
| `invalid_policy_rule` / `policy_too_large` | 规则字段不一致或集合超限 | 先执行校验，按字段路径修复 |
| `invalid_resource_state` | 资源已 disabled、Ticket 已消费/取消或生命周期不允许 | 刷新并重新确认资源状态，不要盲目重试 |
| 按钮为灰色 | 未选择 Mesh/资源、缺必填值、正在加载或二次确认不匹配 | 依次检查选择、表单、serial/公钥和确认文本 |
| 升级后按钮无响应、文案混杂，控制台报 `node.setAttribute is not a function` | 已打开页面仍使用旧客户端，或 HTML 与缓存的 WASM 版本不一致 | 刷新页面以加载同一构建版本的 HTML 和客户端；当前版本按源码自动更新客户端 URL 与 Service Worker 缓存。仍异常时强制刷新并记录客户端 URL 中的 `v` 值 |
| 实时更新停止 | SSE 连接中断、容量限制或游标过期 | 等待自动重连；必要时刷新页面并检查 Control 事件/网络状态 |
| 列表为空 | 未选择 Mesh、角色无资源读取能力、使用了 Relay 过滤或确实无资源 | 检查 URL、角色、Mesh 下拉框和 `relay_id` 参数 |

如果同一操作连续失败，不要反复点击。记录时间、Mesh ID、资源 ID、错误码和 request ID，然后查询审计及服务日志。

## 19. 当前 Web 控制台边界

- Root 和设备私钥不进入网页；设备凭据更新请求由设备执行。旧客户端必须升级并声明 Wire 5 的新增能力位。
- 普通 Relay 资源表单不会部署服务；基础设施任务沿用现有宿主执行器和任务回报。
- “问题与维护”中安装级维护、备份和原生升级依赖已注册且具有当前有效预览的执行器；未配置时显示真实缺失状态。
- 恢复投产、Console/Compose 自动升级不提供虚构执行按钮；按[备份恢复](backup-restore.md)和[升级恢复](upgrade-recovery.md)运行手册执行。
- 策略模拟不产生网络流量；TCP 探测不验证应用身份或互联网全部功能；配置回执、在线 Presence 和目标可达性分别判断。
- 高级表单保留原始技术能力，支持 Relay 区域和路由权重。没有任意字段搜索、历史时序图或集中收集的直连拓扑。
- OIDC、角色和现有能力模型保持不变。auditor 以全局审计为主，不具备资源读取/网格选择能力。

接口见 [api.md](api.md)，安装级运行手册见 [deployment.md](deployment.md)、
[observability.md](observability.md)、[key-rotation.md](key-rotation.md) 和 [incident-response.md](incident-response.md)。

## 20. 日常巡检建议

### 每日

- 查看 Control 顶部状态和外部 `/readyz` 告警；
- 检查在线 Relay 数、在线 Peer 比例和 Presence 分布；
- 检查 `missing`、`expired`、`warning_7d` 凭据；
- 查看审计中的 denied/failure 和未知 actor；
- 确认没有长期未消费且即将到期的 Join Ticket。

### 每周

- 检查 30 天内到期的 Authority、Peer 和 Relay 凭据；
- 检查禁用资源、孤立 Service 和异常标签；
- 用策略模拟覆盖关键允许路径和拒绝路径；
- 对照审计复核批量操作和高风险变更；
- 检查 Relay 负载和区域分布是否需要扩容。

### 重大变更后

- 等待相关 revision 前进；
- 核对新凭据/Authority 生命周期；
- 确认 Relay 和关键 Peer 重新在线；
- 模拟关键 Service 访问；
- 检查审计、Control/Relay/Peer 日志和 Prometheus 告警；
- 按运行手册执行实际端到端连通性验证。

## 23. 发布前五场景界面验收

日常控制台的发布前验收固定覆盖下面五类场景。重点不是确认“功能入口都存在”，而是确认管理员能判断下一步，而且不会看到自己无权执行的动作。

| 场景 | 应看到什么 | 不应出现什么 |
| --- | --- | --- |
| 首次使用 | 没有设备、共享或可检查来源时，给出一个明确的下一步；可写账号可以直接进入添加流程 | 空表格、没有解释的零值统计、要求只读账号去添加资源 |
| 正常状态 | 首页和问题页保持安静，状态信息按需展开 | Control、Relay、凭据序列、底层 Policy 等长期占据日常页面 |
| 异常状态 | “发生了什么 → 影响什么 → 建议下一步 → 重新检查”，证据消失后才确认恢复 | 点击修复动作后立即宣称“问题已解决” |
| 只读权限 | 页面顶部显示“只读模式”；可以查看设备、共享、访问结果和问题；高级入口表述为“高级…信息” | “添加设备”“添加共享”“修改访问”等变更快捷入口，或暗示用户具有写权限的空状态 |
| 手机窄屏 | 设备列表压缩为摘要；访问结果堆叠为卡片；抽屉使用可用宽度；页面没有横向溢出 | 依赖横向滚动才能读懂的多列表格、顶栏塞满偏好设置和动作按钮 |

只读提示依据服务端返回的稳定 capability 渲染，不根据角色名称猜测权限。`resource_read` 允许查看日常网络对象；没有 `resource_write` 时，设备、共享和访问页面不呈现普通变更快捷入口。具有单独信任管理能力的系统工具仍由各自 capability 控制，不能因为页面显示“只读模式”就绕过后端授权。

窄屏回归在 `console-v14.spec.mjs` 中继续检查 `documentElement.scrollWidth <= innerWidth`，并在已有共享数据的访问页确认移动端“共享 / 访问结果 / 详情”标签可见。可再生截图写入 `artifacts/console-v14/screenshots/`。

## 24. 发布候选死路审查（Round 11）

Round 11 在前述五场景回归之上增加一条更严格的发布候选原则：**页面不能要求普通管理员根据禁用控件、后端枚举、旧数据或内部 action 名称自行推断当前状态。**

具体检查项如下：

- 从设备详情进入“共享与访问”时，当前设备已经固定为访问来源。嵌入视图不再重复展示来源搜索或来源下拉框；比较其他设备或设备组时才进入完整“访问”页。
- 概览未选择网络时只说明“先选择一个网络”，不再假设账户正在第一次创建网络。只有网络列表确认为空时，才根据 `trust_manage` 能力分别显示“新建网络”或“当前账号不能新建网络”。
- 添加共享的普通步骤使用“共享类型 / 共享内容 / 查看共享状态”等任务语言；底层资源模型只在高级或开发文档中解释。
- 全局搜索结果把 `device / group / service / subnet / internet` 等后端类型映射为“设备 / 设备组 / 共享 / 网络”，普通界面不直接泄露内部枚举。
- 设备详情读取失败时显示独立错误和“重试”，不会同时保留一个看似正常的加载状态。
- 共享详情重新读取失败、但仍有上一次已加载对象时，必须明确提示“下面是旧信息”；在重新检查成功前，不能把它描述成当前证据。
- 完整“访问”页如果设备或设备组候选加载失败，会显示可恢复错误并允许同时重试两类来源，而不是留下一个不完整的空选择框。
- 日常维护和问题提示优先使用“设备身份”；凭据序列、底层 credential 概念保留在技术详情和高风险撤销操作中。
- 设备详情里的操作记录显示本地化的人类可读动作，例如 `peer.update` 显示为“设备 · 修改”。稳定 action 名称仍存在于审计接口、导出和技术排障数据中。

发布前人工走查任意主页面 → 对象详情 → 下一步动作时，应能直接回答三个问题：**我现在在看谁；这些信息是不是当前的；下一步能做什么。** 任一问题需要查看内部字段或猜测控件含义，均应视为发布前 UX 缺陷。

## 25. 交互安全与键盘无障碍验收（Round 12）

发布候选界面除五场景和死路审查外，还要通过以下交互安全检查。这里不改变权限模型或业务语义，只验证操作不会因焦点、重复提交或未保存状态而产生歧义。

- **模态焦点**：打开设备详情、共享详情、全局搜索、通知中心或创建网络窗口后，Tab / Shift+Tab 只能在当前窗口中循环；关闭后焦点回到触发入口。模态打开期间背景区域不参与键盘操作。
- **详情 Tab**：设备详情的“状态 / 共享与访问 / 维护”和共享详情的“状态 / 共享信息 / 谁可以访问 / 网关路径”使用标准 ARIA Tab 语义。方向键在相邻页签间移动，Home / End 跳到首尾页签；当前页签只有一个 `tabindex=0`。只读数据加载时仍可切换页签；写入提交或拒绝丢弃草稿时保持当前选择和焦点。
- **未保存修改**：修改设备名称/位置、邀请设置、共享向导、共享设置、授权、设备身份更新或退役确认后，关闭详情、切换详情页签、切换来源或离开页面都必须先确认。仅打开表单但没有更改内容时不应弹出误报。
- **防重复提交**：任何网络写操作开始后立即进入 busy 状态；相关字段和提交按钮禁用，并使用“正在保存… / 正在检查… / 正在提交…”等文案。事件处理器本身也检查 busy，不能只依赖按钮的 `disabled`；提交仍在进行时，关闭窗口或按 Escape 不应中断当前操作。
- **反馈语义**：需要立即注意的失败使用 `role="alert"`；保存成功、提交完成和恢复确认使用 `role="status"` 或 `aria-live="polite"`。用户编辑字段后应清理已经失效的旧错误，避免把过时错误当作当前结果。
- **减少动态效果**：浏览器或操作系统声明 `prefers-reduced-motion: reduce` 时，Console 不依赖动画传达状态，并关闭非必要动画和滚动过渡。
- **错误后可继续操作**：网络请求失败后，表单重新启用，已有输入继续保留；用户修正输入或点击重试即可继续，不要求刷新整个页面。

建议发布前至少用一次纯键盘完成：**设备列表 → 打开设备详情 → 方向键切换到维护 → 返回状态 → 关闭详情 → 打开全局搜索 → 关闭并确认焦点返回**。随后在一个有写权限的测试网络中验证一次“提交中连续按 Enter”不会产生重复请求。

## 26. 发布候选冻结与最终验收（Round 13）

Round 13 起不再继续调整日常控制台的信息架构。发布候选阶段只修复真实构建、Playwright、键盘/无障碍、权限、恢复和部署演练中发现的缺陷。完整 RC 顺序、升级/回滚演练和当前已知限制统一记录在[发布候选检查](release-candidate.zh-CN.md)。

在干净且已提交的 Git 工作区可运行：

```sh
scripts/run-release-candidate.sh console
```

该命令把 core 构建/测试、v14 Console 浏览器回归和部署契约检查绑定到同一 commit，并把日志写入 `artifacts/release-candidate/`。结果固定为本地候选信息，不会关闭正式 release evidence gate。需要完整本地 gate 与隔离 Linux 更新/回滚机制演练时使用 `scripts/run-release-candidate.sh full`。

发布前仍需人工确认：纯键盘主流程、焦点返回、屏幕阅读器/视觉复核、完整应用的一次性安装与恢复，以及正式 gate 所要求的物理 Android、真实网络、长期 soak、容量和外部安全证据。自动 axe、管理 fixture 或合成 updater 角色程序均不能替代这些边界。

### 添加设备时分组

“设备用途”已移除，设备名称和位置说明仍可在详情中编辑。添加设备时可多选现有设备组，也可不选，加入后从 **设备 → 设备组** 调整。

所选组随邀请固定，在成功入网（人工确认模式下为批准时）与设备身份一起提交。未批准时不会提前加入组；组在此期间被删除或超出成员上限，会阻止本次入网，请重新创建邀请。旧邀请保持原来的准入条件，不会把历史用途转换成设备组。

表单显示所选组当前已启用的共享允许规则及协议、端口。此列表不是连通性检查；附加条件、拒绝规则、共享暂停以及入网前后规则的变化仍会影响实际访问。不分组也不代表绝对无权限，已有直接设备规则、标签规则等仍按正常策略执行。
